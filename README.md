# job-alert-agent

בוט טלגרם שעוקב אחרי דפי קריירה של חברות ומתריע על משרות חדשות (רלוונטיות
לישראל, כולל remote מסויג). רץ כולו על GitHub Actions - אין שרת.

## איך זה עובד

- **פרופיל = רישום.** כל חברה היא קובץ `profiles/<slug>.json`, מבנה
  מלא ב-`SKILL v2` של `career-site-profiler`. אין `companies.json` נפרד.
- **ה-dispatcher** (`src/fetchers/__init__.py`) קורא `fetch_type` מהפרופיל
  ומפנה למודול המתאים (`api.py` / `html.py` / `browser.py`), שקוראים בעצמם
  שדות נוספים (`platform`, `pagination.method`, `israel_filter.structure`)
  כדי לבחור אסטרטגיה. חברה חדשה על שילוב קיים = קובץ JSON חדש, אפס קוד.
- **הזיהוי "משרה חדשה"** רץ תמיד על `Job.id` (מזהה ATS או קישור מנורמל),
  לעולם לא על טקסט תצוגה - כדי ששינוי קוסמטי אצל החברה לא יגרום להתראה
  כפולה.
- **שער בריאות**: אם חברה שהחזירה משרות בעבר מחזירה פתאום 0, זה נחשב
  כשל (סלקטור שנשבר), לא "אין משרות". ה-state לא נדרס, ומתקבלת התראת
  תחזוקה אחרי שני כשלים רצופים.
- **שרשרת מסננים** (`src/filters.py`) רצה בין ה-diff לשליחה, ומחליטה מה
  *מוצג* — לא מה נחשב חדש. ראה למטה.

## מסנן ניסיון

ברירת מחדל: **פעיל**, חוסם משרות שדורשות **יותר משנה** ניסיון.

דרישת הניסיון לא נמצאת ברשימת המשרות (ה-listing מחזיר רק
`id`/`title`/`location`/`url`), אז יש שכבת פירוט (`src/detail.py`) שמביאה
את תיאור המשרה לפי `detail_fetch` בפרופיל — `inline` (התיאור כבר הגיע
ב-listing, אפס בקשות), `html`, `playwright`, או `none`.

**תמיד לבדוק `inline` לפני שבונים בקשה לכל משרה.** זה כלל
cheap-to-expensive של הפרויקט, והוא הוכיח את עצמו: גם Lever וגם Greenhouse
מחזירים את התיאור המלא כבר ב-listing, כך ששתי החברות המאומתות עולות אפס
בקשות נוספות. `inline_field` תומך גם בשדה שהוא **מערך של סקשנים**
(`[{text: כותרת, content: "<li>..."}]`, הצורה של Lever) ולא רק במחרוזת —
`detail.render_sections` הופך אותו ל-HTML לפני הפרסור, כולל שמירת הכותרות,
כי הכותרת היא מה שמקדם בולט לא-מסומן ל"חובה".

**סדר הפעולות — קריטי:**

```
fetch → dedupe → diff מול state → משרות חדשות
      → כתיבת כל המזהים החדשים ל-state   ← לפני הסינון
      → סינון לפי כותרת → הבאת תיאור → שרשרת מסננים
      → שליחה של מה ששרד
```

ה-state נכתב **לפני** הסינון בכוונה: state = "כל מה שנראה אי פעם", סינון =
תצוגה בלבד. אילו משרות שנחסמו היו נשארות מחוץ ל-state, כל אחת מהן הייתה
נראית חדשה בכל ריצה ודף הפירוט שלה היה נמשך שוב ושוב לנצח.
**התוצאה המקובלת:** כיבוי המסנן לא ישלח רטרואקטיבית משרות שנחסמו כשהיה
פעיל. אין מנגנון replay, במכוון.

**Fail-open**: אם לא נמצא מספר — המשרה **נשלחת** עם דגל. הפסד של משרה
רלוונטית יקר בהרבה משתי שניות גלילה. גם כשל בשכבת הפירוט (404, סלקטור
מת, timeout) הוא "לא ידוע" — הוא **לא** מסמן את החברה ככשל, לא חוסם את
כתיבת ה-state ולא מפיל את הריצה. זה נפרד לגמרי מ-`health`/
`expected_min_jobs`, שנוגעים ל-listing ולא נגעו בהם.

**שלוש רמות דגל** (כל השלוש נשלחות — הדגל רק ממיין):

| דגל | משמעות |
|---|---|
| `✅ ניסיון: עד שנה` | נמצא מספר, והוא מתחת לסף |
| `⚠️ לא צוינה דרישת ניסיון` | לא נמצא מספר בכלל |
| `🔶 לא צוין מספר, יש סימני ותק` | אין מספר, אבל יש `proven experience` / דרישת תואר מתקדם |

הרמה השלישית קיימת כי לפי נתוני Indeed Hiring Lab (ארה"ב, אפריל 2024) רק
כ-30% מהמשרות מציינות מספר שנים — כלומר "לא ידוע" הוא הרוב, ובלי הפרדה
נוספת הדגל היה חסר משמעות.

**סינון לפי כותרת** חוסם `senior`/`lead`/`staff`/`principal`/`manager`
ועוד באפס בקשות. כותרת שנשמעת ג'וניורית **לא** מזכה במעבר אוטומטי: לפי
ניתוח LinkedIn כ-35% מהמשרות המסומנות "entry-level" דורשות 3+ שנים.

**פקודות:**

```
/filter                    מצב כל המסננים
/filter experience on|off  הדלקה/כיבוי
/minexp 2                  שינוי הסף (בשנים)
/minexp strict on|off      במצב strict, "לא ידוע" נחסם במקום להישלח
/stats                     מונים: נחסם לפי כותרת / נמצא מספר ועבר /
                           נמצא מספר ונחסם / לא ידוע / לא ידוע עם סימני ותק
```

ההגדרות נשמרות ב-`state/filters.json` שה-workflow כבר עושה לו commit —
לכן אפשר לשנות אותן מהטלפון בלי commit ובלי לגעת ב-workflow. המונים
ב-`/stats` הם הדרך היחידה לדעת אם המסנן באמת עובד או רק נראה עובד: נתוני
ה-30% הם אגרגט אמריקאי, ולא בטוח שהם נכונים למשרות ישראליות.

## הוספת חברה

1. פתח שיחה עם Claude, בקש להוסיף את החברה - זה מפעיל את הסקיל
   `career-site-profiler`. הסקיל הוא גם מה שקובע את `detail_fetch` של
   החברה (ומאמת אותו מול URL אמיתי של משרה) - לא מנחשים אותו ידנית.
2. שמור את ה-`profile.json` שהתקבל תחת `profiles/<slug>.json`.
3. הרץ `python run.py --seed` (ידני, דרך `workflow_dispatch` או מקומית)
   כדי לזרוע state בלי לשלוח התראות על כל המשרות הקיימות.
4. מהריצה הבאה של ה-cron החברה נכנסת למעקב הרגיל.

**`/add` בטלגרם לא עושה את זה אוטומטית (v1 מכוון)** - הוא רק אומר
שצריך סשן פרופיילינג ידני. `/remove <slug>` מכבה חברה (`enabled: false`)
בלי למחוק היסטוריה. `/list` מציג את כל החברות וסטטוס שלהן (שמות בלבד,
לא משרות). `/jobs <slug>` שולף בזמן אמת (לא מה-state) את המשרות הפתוחות
הרלוונטיות לישראל כרגע אצל אותה חברה - עד 20 בהודעה אחת (מגבלת 4096
תווים של טלגרם), עם קישור לעמוד הקריירות המלא אם יש יותר.

**פקודות טלגרם לא רצות ברקע.** אין תהליך שמאזין - הן נקראות פעם בכל
ריצה של ה-cron (piggyback), אז זמן התגובה הוא עד מרווח ה-cron (3 שעות)
+ עיכוב GitHub הרגיל. זו החלטת עיצוב מכוונת: cron ייעודי לפקודות היה
שורף לבד את כל מכסת ה-Actions של רפו פרטי.

## הרצה מקומית

```bash
pip install -r requirements.txt
python -m playwright install --with-deps chromium   # רק אם יש חברת playwright
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_CHAT_ID=...
cd src
python run.py --seed   # בפעם הראשונה
python run.py          # ריצה רגילה
```

## סטטוס נוכחי

- `mobileye`, `wiz` — פרופילי API (Lever/Greenhouse), **אומתו חי** ב-2026-08-11:
  מובילאיי מחזירה 122 משרות רלוונטיות לישראל (`expected_min_jobs: 20`,
  `zero_is_plausible: false`), Wiz מחזירה 0 (ה-board האמיתי שלה מכיל כרגע
  רק 2 משרות בסך הכל, שתיהן מחוץ לישראל - `zero_is_plausible: true`
  נשאר נכון). ה-state כבר נזרע (`state/seen/`), אין seed gap.
- `wix` — פרופיל `playwright` (אין ATS מוכר, דף הקריירה בנוי על הפלטפורמה
  של Wix עצמה), **אומת חי** ב-2026-08-11 בשתי דרכים: בדיקת DOM/network
  בדפדפן, ו-הרצה אמיתית של `fetch()` שהחזירה 15 משרות בתל אביב
  (`expected_min_jobs: 6`, `zero_is_plausible: false`). הפילטר לישראל
  רץ `post_fetch` על הרשימה המלאה (לא על ה-location picker של האתר - נשבר
  כשמנסים לסנן שתי ערים בבת אחת, ראה `israel_filter._note` בפרופיל).
  **Seed gap פתוח** - אין `state/seen/wix.json`; יש להריץ
  `python run.py --seed` לפני שההתראות הרגילות ייכנסו לתוקף עבור החברה
  הזו.
- **מסנן ניסיון — `mobileye` ו-`wiz` עברו ל-`schema_version: 3`** עם
  `detail_fetch` **מאומת חי ב-2026-08-12**, שניהם `method: inline` (אפס
  בקשות נוספות):
  - `mobileye` → `inline_field: lists`. ה-listing של Lever כבר מכיל את כל
    התיאור, אז אין צורך ב-`method: html`. השדה נבחר אחרי בדיקה שדה-שדה מול
    הפרסר על 25 משרות אמיתיות: `description`/`descriptionBody` מכילים רק
    את פסקת הפתיחה והחזירו מספר ב-0 מתוך 25, ואילו `lists` החזיר ב-18.
  - `wiz` → `inline_field: content` עם `content_is_html: true` (השדה מגיע
    HTML **וגם** HTML-escaped — אומת חי). זו הדרך היחידה שם: עמוד משרה של
    Greenhouse מגיש רק את טופס ההגשה.
  - **תוצאה חיה על Mobileye:** מתוך 122 משרות רלוונטיות לישראל, 5 עוברות
    את המסנן (95% נחסמות) — 63 לפי כותרת, 54 לפי מספר שנים מפורש. שיעור
    ההכרעה הוא **91%**, לעומת ~30% שהיו הבסיס האמריקאי לתכנון: משרות
    הייטק ישראליות מציינות מספר שנים הרבה יותר מהממוצע האמריקאי.
  - שים לב: אף משרה ב-Mobileye לא דורשת שנה או פחות (המינימום שנמצא הוא
    שנתיים, ב-6 משרות), ולכן `passed_with_number` הוא 0. `/minexp 2` יפתח
    את 6 המשרות האלה.
- `wix` — **עדיין `schema_version: 2` ובלי `detail_fetch`**, כלומר המסנן
  עובד עליה ברמת הכותרת בלבד וכל השאר נשלח עם `⚠️`. זה fail-open תקין ולא
  באג. צריך סשן `career-site-profiler` כדי לקבוע איך מגיעים לתיאור של משרה
  שם (ה-listing הוא `playwright`, ועמוד המשרה עצמו לא נבדק).
